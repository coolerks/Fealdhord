# 需求分析与首版决策

日期：2026-11-04。输入为用户提供的完整 v2.0 指令、当前用户明确的调研范围和仓库证据。本轮没有真实用户访谈或可用性实验；下述角色、优先级与默认值属于产品分析，不伪称市场结论。

## 用户任务与痛点

主要角色假设是重度个人订阅阅读者：每天快速扫描新内容，深入阅读少数文章，按主题组织，之后通过搜索和收藏找回。AI 使用者是同一用户的增强场景，需要跨模型理解内容和安全执行整理操作，不需要另建一套聊天主应用。

核心阻碍是内容多而阅读空间有限、文章图片质量不一、重复抓取或 AI 改写用户组织、模型协议差异和工具副作用不透明。需求因此不是“集成尽可能多的库”，而是 RSS 独立成立、阅读有两种可用投影、状态可信、额外能力可选且可控。

## 歧义、决定及代价

| 原始未定细节 | 本轮拟定 | 为什么及代价 |
| --- | --- | --- |
| 瀑布流打开 Reader 的形式可选 | 宽浏览＋右抽屉，窄窗口覆盖浏览区 | 保留浏览空间，需锚点与焦点恢复 |
| 未配置 AI 的精选行为 | 解释性空态，无假推荐 | 真实表达能力，需要引导而非随机内容 |
| 删除 Feed 的数据影响 | 归档源、保留已有文章 | 降低损失，未来永久清理需单独设计 |
| 分类多来源如何存 | 每来源独立行，manual tombstone | 保留可解释证据，查询略复杂 |
| 默认图像与网页额外请求 | 订阅关联图片，网页补图默认关 | 平衡预览与隐私，部分文章缺图 |
| 缺凭据服务的 fallback | 仅会话内存 | 不静默落明文，重启后需重输 |
| 中文短查询 | 显式二字／单字 token＋连续文本校验 | 召回可控，但索引成本待规模实验 |
| 新旧 MCP 协议 | 官方 SDK 协商，不手写固定旧握手 | 降低协议漂移，需要互操作矩阵 |

用户授权自主调研，因此本轮形成完整可逆方案，并在最终摘要中评审。默认参数可在实现验证后调整，但涉及隐私范围、删除语义、权限放宽或新增外发行为的重大变化必须重新评审，不能用“调优”掩盖产品改变。

## 未证结论与完成边界

没有对用户量、性能、平台兼容或库维护健康作无证保证。环境故障和技术原型进入对应阶段门禁；本轮输出是可评审规格，不是可运行产品。需求覆盖由 113 项机器清单核验，测试观察点由具体规格定义，不能仅以章节映射声称实现完成。
