# 多渠道通知与 AI 定时任务实施方案

日期：2026-11-21。本文保留批准的实施设计。运行能力与实机验收状态见 [通知契约](../../../docs/04-specs/notifications.md)。随折栈 Go 进程运行，完全退出后在下一次启动时自动补齐。本文落实 [设计评审](research/notification-design-review.md) 和 [渠道调研](research/notification-channels.md)。

## 1. 业务契约

| 编号 | 行为 | 可观察验收 |
| --- | --- | --- |
| N01 | 一条规则可选多个渠道和分类。分类可选「全部」或指定分类，子分类范围沿用阅读页。首次订阅历史建立基线，之后只推送首次发现的文章。 | 两个渠道同时投递，一个失败时另一个成功。两个分类命中同一篇文章，同一规则各目标只有一份。 |
| N02 | 支持逐条和每日汇总。每日独立设置收录时间范围、发送时间和时区。标题、正文、首图按规则选择。 | 跨午夜、无内容、缺有效链接和缺首图都有确定输出。切换模型或关闭 AI 不影响文章通知。 |
| N03 | 启动或休眠恢复时，补发队列中的未完成内容，且从到期订阅刷新中纳入此前未入库的新文章。 | 退出三天后，错过窗口可查，已确认的目标和片段不重发。文章在源站 RSS 中已不可见时，无法从本机重建。 |
| N04 | AI 可通过自然语言创建一次性、每日、工作日和指定星期的任务，也可查看、修改、暂停、恢复和删除。 | 「每天 20 点把科技文章摘要发给飞书和 Telegram」生成结构化确认；确认后管理页显示下一次运行和目标，拒绝后无任务。 |
| N05 | 九个渠道纳入同一界面。每个连接按实际接收能力启用即时或定时推送。 | 独立真实账号验收文字、链接、首图及隔时主动投递。微信或 QQ 能力未验证时，界面显示未验证及对应测试入口。 |

## 2. 代码落点

| 区域 | 计划改动 |
| --- | --- |
| SQLite / sqlc | 在 `migrations/` 加下一号迁移，`internal/database/queries/` 加通知查询，生成 sqlc 绑定。数据库保留现有文章 ID、分类视图和 Store 写事务边界。 |
| RSS | `internal/database/library.go` 现有 `upsertArticle` 传出是否新增。 `internal/database/feeds.go` 的刷新事务在真新增且刷新已有基线时同事务追加事件。初次成功刷新覆盖直接订阅、OPML、新建和恢复场景；已有库升级保留其已完成的刷新基线。 `CommitFeed` 继续提供原文章 ID 列表给媒体。 `SetAfterCommit` 只用来唤醒通知处理。 |
| Go 服务 | 拟新增 `internal/notification` 存放规则、消息格式、渠道适配与投递，`internal/schedule` 负责日历、到期领取和固定任务执行。通过窄接口互连。 `main.go` 装配、启动、绑定 Wails API，退出时停止接单并取消在途工作，最后关闭 Store。 |
| AI | `internal/appagent/app_tools.go` 复用 Registry 注册工具，在模型上下文提供本机时间、时区及能力。后台执行复用已有 `ai.Model` 接口和模型配置选择，按任务范围查询文章。 |
| 前端 | `frontend/src/features/settings/` 的「通知」增加连接、规则、历史入口。AI 对话复用工具确认，AI 侧栏和斜杠命令打开同一个「定时任务」管理页，支持编辑、暂停、恢复和删除，并显示下次执行与运行历史。同步生成 `frontend/bindings`。 |

RSS 恢复使用既有刷新服务的到期查询、并发限制和取消机制。启动时给恢复刷新批次附进程恢复标识，普通定时刷新沿用原行为。成功的订阅按自身进度结算，无需等所有源成功。对已经有过基线但恢复请求失败的订阅，保留恢复标识到该订阅下一次成功刷新或取消订阅，迟到文章走补充批次。

## 3. 数据、事务与状态

| 表或实体 | 主键和关键约束 |
| --- | --- |
| `notification_channels` | `id`、平台、目标身份、显示名、凭据引用、验证结果及其版本、启停和 `revision`。平台与目标变更时失效旧验证。 |
| `notification_rules` 及选择关联 | 规则 ID、模式、正文和首图选项、时区、收录窗口、启停、`revision`；多对多保存渠道与分类 ID。 |
| `notification_article_events` | 单调事件序号，唯一文章 ID，订阅 ID、不可变 `discovered_at`、可用的来源发布时间和恢复标识。 |
| `scheduled_tasks` | 任务 ID、`revision`、任务种类、结构化日历、范围、下一到期时点、授权版本和指定目标。每日文章规则可关联同一调度机制。 |
| `scheduled_runs` | 唯一 `(task_id, occurrence_key)`。状态、计划时间、窗口边界、租约、结果引用、合并次数。补跑合并的时点仍保存覆盖关系。生成结果和新投递记录同事务提交。 |
| `notification_items`、`notification_deliveries` | 文章项唯一 `(rule_id, article_id, channel_id)`，连续片段唯一 `(batch_id, channel_id, part_no)`。保留片段对应文章项、稳定的请求标识、目标身份快照、出队时间和平台返回摘要。 |

事务顺序：① 文章与事件同事务。② 消费事件时匹配规则，将去重项与游标同事务推进。③ 任务到期时同事务领取唯一运行；完成模型调用后，将生成结果和待发片段同事务保存。④ 投递前领取发送租约，网络请求在事务外，返回后登记结果。修改配置使用 `revision`，工作进程出队前复核规则、目标、权限和启停状态。

建议投递状态为 `pending → claimed → sending → accepted`。领取后尚未开始网络发送即可安全恢复。进入 `sending` 后进程退出、超时或回包丢失时，记 `unknown`，仅在平台支持幂等请求或可确证未送出时自动续投。429 等明确拒收的可恢复错误按平台限制退避，有限次数，到限记 `failed`。在设置中允许用户查看并显式重送结果未知的片段。禁用渠道或撤销授权取消未开始的投递。换目的地创建新目标身份，旧队列不跟随。

历史仅存时间、状态、脱敏错误、任务和渠道引用及必要的文章／结果关联。查询用游标分页。清理日志和生成结果与投递去重分开，不能将清理历史变成重新投递旧文章的触发条件。升级新迁移保留现有阅读数据，旧程序使用升级前快照回退，禁止原位降级新数据库。

## 4. 时间、恢复和输出

- 日历提交结构为 `{kind, timezone, local_time, weekdays, once_at}`，按种类只接受适用字段。每天固定当地时刻，按明确的 IANA 时区计算 UTC 时点。每日规则将最近已结束的配置窗口配对目标日期，收录区间使用 `[start, end)`，跨午夜显式换日。夏令时缺失时点顺延，同一重复时点只运行一次。后续改时间以新版本下一个有效时点为准，暂停期间不创建补跑记录。
- 启动先恢复已经持久化的待发记录，再触发到期扫描与 RSS 恢复。已有队列可立即发。窗口是否因源站无内容而为空、因刷新失败暂缺、或已收到补充文章分别记录。恢复批次大于一条平台消息时按片段拆分，历史标出覆盖的日期及文章数。
- 新文章用首次发现时间归属。若退出期间文章在恢复时才发现，而且 RSS 提供可信的离线期间发布时间，可归入对应日期；无可信时间时归为「恢复时新发现」。这些只是分组方式，共用唯一文章投递键。逐条规则允许首次 AI 分类结果补入此前未匹配的文章；分类编辑不把已投递文章变成新文章。
- 统一内容对象包含标题、有效原文 URL、可选可读纯文本、可选首图。Markdown、卡片或纯文本在适配器层生成。缺图仍发文字；私有图片只在目标支持上传且允许外发时送出，不把本地媒体地址给外部平台。Webhook URL、签名密钥和 Bot Token 存系统凭据存储，绑定响应只返回脱敏信息。

## 5. 接口与权限

| 操作 | 拟定入口与约束 |
| --- | --- |
| 连接 | Wails `ListChannels`、`SaveChannel`、`TestChannel`、`DeleteChannel`，另有微信绑定启动／查询／取消。输出含可用能力和错误原因。测试发送只由用户明确触发。 |
| 规则 | `ListRules`、`PreviewRule`、`SaveRule`、`SetRuleEnabled`、`DeleteRule`。预览生成下一时间窗与样例消息，不创建外部投递。 |
| 任务与历史 | `ListTasks`、`GetTask`、`PreviewTask`、`SaveTask`、`SetTaskState`、`DeleteTask`、`ListRuns`、`ListDeliveries`。写操作带预期版本。历史查询使用游标和过滤。 |
| AI 工具 | `notification.channel.list`、`notification.rule.list`、`notification.send`；`schedule.list`、`schedule.get`、`schedule.create`、`schedule.update`、`schedule.pause`、`schedule.resume`、`schedule.delete`。写入和外发复用工具确认。只接受已保存目标 ID，确认卡解析真实目标及数据范围；确认后核对配置版本。 |

后台任务初版支持固定提醒、文章筛选、范围受限的 AI 摘要。模型可以生成正文或建议修改任务，计划的触发器、目标、范围和执行动作由结构化记录决定。摘要可用已经确认的数据，包含来源链接。禁止在后台摘要回合挂载会变更配置或发往任意目标的工具。现有 MCP 公共工具清单保持显式授权，新工具不会因注册而自动对外开放。

## 6. 实施顺序与验收

1. **优先验证协议边界。** 取得授权的专用接收目标后，个人微信验证扫码、令牌失效、退出重启及无新入站消息的隔时发送。QQ 按私聊、群、频道分别验证主动方式。其余七个平台从官方接口实现；每个平台独立记录发送能力和指标。全部接入按一个功能交付，开发可分职责提交。
2. **文章事件与迁移。** 在临时库验证首次订阅、OPML 初次刷新、304、内容更新、重复刷新与事务回滚。检查旧库升级不会产生历史推送。
3. **调度和队列。** 用受控时钟和可注入发送器验证 DST、跨午夜、重启与唤醒、租约竞争、部分渠道成功、未知结果、限流、取消以及权限变化。
4. **渠道与设置界面。** 用本地模拟端点验收载荷、签名、错误码和图片降级。通过设置建立两个真实目标做规则演示。复用共享表单，可搜索多选适用于渠道、分类和时区。测试连接和真实投递使用专用接收目标。
5. **AI 自然语言与整体验收。** 串联创建→确认→到期→运行→发送→重开恢复→修改／暂停。验证拒绝动作不落任务、后台权限不会扩大、已存摘要恢复后不再次请求模型。运行迁移及相关 Go 测试、竞态检查、Wails 绑定生成、前端类型、lint、测试与构建。验收清单分别记录模拟通过与实机通过。

## 收件目标配对

三步向导支持在内存里临时接收「配对」事件，用户选中目标并保存后才写入渠道配置。接收平台与字段见 [后端契约](../../spec/backend/notification-pairing.md)。企业微信自建应用需要单独的消息回调接入，当前继续手填成员 ID。

QQ 私聊配对回归补齐正式与沙箱路由，收到网关心跳确认后再提示等待消息。QQ 手机端真实账号仍待验证。

QQ 手机端反复提示未连接时，网关 ACK 只能证明连接存活。正式域名和鉴权路由参照 [腾讯 SDK](https://github.com/tencent-connect/qqbot-nodejs/tree/main/src/protocol/api)，使用 READY 昵称及首个实际聊天事件区分身份和入站问题。

设置向导第 4 步自动发送四位收件校验码，校验绑定目标和渠道修订版。关闭向导保留配置及待验证目标。

渠道表单为九个平台提供「操作步骤」，按应用机器人或 Webhook 接入方式显示配置说明。官方文档使用纯文字链接，QQ 两种环境统一打开 `https://bot.qq.com/`，个人微信只显示操作步骤。

文章发送渠道使用 shadcn/ui Combobox 的标签多选形态。选中 ID 是同步标签、全选开关与发送目标的唯一来源。回归覆盖搜索、键盘选择、逐项选满、标签移除、全选清空、Escape 及最终发送参数。

飞书与 Lark 复用 `PairingStatus.received_message` 区分 SDK 握手与用户私聊。应用订阅接收消息后仍需开通私聊权限并发布。同一个 AppID 有多个长连接时，同一事件只会投递给其中一个。回环验证 SDK 收件和 Open ID 提取，真机事件投递待验证。

钉钉应用模式的凭据表单采用 Client ID 和 Client Secret，操作步骤分别说明 Stream 接收配置与企业内机器人发送消息权限。钉钉群 Webhook 继续使用 Webhook URL 与加签密钥。

钉钉配对补齐官方显式 `:443` 网关地址。回归用官方响应形态证明旧校验会在拨号前拦截，并覆盖修复后的心跳确认、配对回调、受信域名校验和连接失败诊断。

企业微信自建应用校验码失败保留数字错误码和本地排查提示。区分取令牌与发送错误，识别成员无效或缺少许可的响应，验证失败时销毁当前验证码。
